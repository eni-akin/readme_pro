# Deliberate presentation

## Opening and rhythm

Give the name, specific description, useful action links, and representative proof enough visual space. Keep a decorative banner proportionate to the information it contributes. Preserve established branding; a logo is optional. Use a logical heading hierarchy, compact paragraphs, and parallel capability bullets. Reserve tables for information readers compare and diagrams for relationships that prose obscures.

Use the project's tone. Restraint is a default when no style is specified, not a ban on personality, centered introductions, or tasteful emoji. Choose a coherent treatment rather than mixing multiple decorative systems. Replace generic praise with observable behavior. Avoid repeated introductions, technology badge walls, visitor counters, unsolicited star requests, and exhaustive dependency lists.

## Proof and assets

Use real repository assets or authorized captures showing a recognizable task. For a CLI, readable output may communicate better than a GIF. For AI/data work, include labels, units, and context with figures. For libraries, executable code and its result often provide the strongest demonstration.

Reuse the repository's asset convention; if none exists, `docs/assets/` is a reasonable home. Use descriptive filenames and relative links for local assets. Check asset reuse rights and strip private data from screenshots. Essential instructions must remain available as text. Give informative images meaningful alternative text.

Inspect images at practical GitHub widths and against light and dark backgrounds. Prefer opaque backgrounds or existing theme variants where transparency makes content disappear. Keep animations few and focused; a static preview linking to a longer recording often reads better. A diagram must describe implemented components, not proposed architecture disguised as current behavior.

## Navigation and Markdown

Use GitHub-compatible Markdown and modest supported HTML only where it improves the page. Do not depend on JavaScript, arbitrary CSS, or unsupported embeds. Name fenced-code languages; distinguish commands from their output and keep copyable commands free of shell prompt prefixes. State the working directory when it changes.

Use descriptive link text. Link local files relative to the README and verify heading fragments. Preserve existing anchors referenced elsewhere or provide compatible targets when headings change. Add a manual contents list only when it helps readers navigate a substantial page.

## Badges and trust

Add badges only when they answer a useful question and their targets match this repository, workflow/branch, package, or license. A badge reflects its underlying source; it is not evidence of unmeasured quality. Use a compact row when appropriate, without a fixed badge quota. Omit unknown badge targets instead of filling placeholders.

## Detail placement

Summarize enough to help the next decision and link the rest. Common destinations are existing architecture docs, API references, benchmark reports, contribution guides, changelogs, security policies, and model/data documentation. Create supporting files only when the assignment needs them. Keep important limitations and costly prerequisites visible rather than hiding them in collapsible sections.
